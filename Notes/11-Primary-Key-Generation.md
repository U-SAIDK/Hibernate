# 11 · Primary Key Generation

## Introduction

Every entity needs a unique identifier (`@Id`). Rather than assign ids by hand, you let Hibernate/the database generate them with `@GeneratedValue`.

## Why this concept exists

Ids must be unique and are usually meaningless surrogate keys. Generating them manually is error-prone and racy under concurrency. Delegating generation to the database (or a well-defined strategy) is safe and standard.

## The strategies

| Strategy | How the id is produced | PostgreSQL fit |
|----------|------------------------|----------------|
| `IDENTITY` | Auto-increment column; DB assigns on INSERT | Works; **blocks JDBC batching** |
| `SEQUENCE` | A database sequence object; Hibernate asks for next value | ✅ Recommended default |
| `AUTO` | Hibernate picks per dialect (SEQUENCE on PostgreSQL) | Fine |
| `TABLE` | A separate table simulates a sequence | ❌ Legacy, avoid |
| UUID (`@GeneratedValue` on a `UUID` field) | 128-bit unique value | Good for distributed ids |

## Important annotations

```java
// IDENTITY — database auto-increment
@Id @GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

// SEQUENCE — recommended on PostgreSQL, allows batch inserts
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "seq_gen")
@SequenceGenerator(name = "seq_gen", sequenceName = "demo_seq", allocationSize = 50)
private Long id;

// UUID
@Id @GeneratedValue
private UUID id;
```

## Simple example

▶️ Runnable: `com.example.identifiers.IdentifierDemo` — persists one entity of each strategy and prints the generated ids.

## Explanation of the example

- The `IDENTITY` entity gets its id only *after* the INSERT (the DB decides it).
- The `SEQUENCE` entity gets its id *before* the INSERT (from the sequence), which is why Hibernate can batch many such inserts.
- The `UUID` entity gets a random 128-bit id, generated by Hibernate.

## IDENTITY vs SEQUENCE (the important trade-off)

- **IDENTITY** forces Hibernate to run the INSERT immediately to learn the id, so it **cannot batch** inserts. Fine for low volume.
- **SEQUENCE** lets Hibernate fetch ids up front (and cache a block via `allocationSize`), enabling efficient **batch inserts**. Preferred for anything write-heavy on PostgreSQL/Oracle.

## Best practices

- On PostgreSQL prefer `SEQUENCE` (with a sensible `allocationSize`) over `IDENTITY` for write-heavy tables.
- Use surrogate keys (generated id), not natural/business keys, as the primary key.
- Use `Long` for numeric ids; `UUID` when you need globally unique ids.

## Common mistakes

- Using `IDENTITY` on a bulk-insert table and wondering why batching doesn't work.
- Setting the id manually on a `@GeneratedValue` entity.
- `TABLE` strategy (slow, legacy) — avoid.
- Mismatched `allocationSize` between the entity and the actual DB sequence increment.

## Summary

Use `@GeneratedValue` to let the database/Hibernate assign ids. `SEQUENCE` is the modern default on PostgreSQL (batch-friendly); `IDENTITY` is simple but blocks batching; `UUID` suits distributed systems.

## How this appears in Spring Data JPA

The annotations are identical — Spring Data JPA changes nothing here. What changes is that this now matters for **`saveAll()`** performance: with `IDENTITY`, Spring/Hibernate can't batch the inserts; with `SEQUENCE` (plus `spring.jpa.properties.hibernate.jdbc.batch_size`), a `saveAll()` of thousands of rows becomes a handful of batched round-trips. This is a classic Spring performance tuning point that traces straight back to your id strategy.
